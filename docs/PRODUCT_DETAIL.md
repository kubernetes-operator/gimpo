# gimpo 상세 설명서

> **"백업이 있는지"가 아니라 "복구가 되는지"를 매일 증명하는 쿠버네티스 백업 운영 대시보드**
> 버전 0.4.0 · 함께 보기: [기술 설명서](TECHNICAL_SPEC.md) · [사용 설명서](USER_GUIDE.md) · [운영 매뉴얼](OPERATIONS_MANUAL.md)

---

## 1. 왜 만들었나

백업 도구를 설치했다고 백업이 지켜지는 것은 아닙니다. 이 프로젝트를 시작할 때 실제로 이런 상태였습니다.

| 겪은 문제 | 결과 |
|---|---|
| 설정 오류로 모든 백업이 **몇 주간 검증 실패** | 아무도 몰랐다 |
| 저장소 지연으로 볼륨 백업이 **13일째 멈춤**, 뒤로 17건 대기 | 아무도 몰랐다 |
| 백업 삭제 요청 **79건이 처리되지 않고 쌓임** | 저장소가 1TB 가까이 찼다 |
| 백업 대상에 **백업 저장소 자신**이 포함 | 매달 100GB 낭비 + 시간 초과 |
| 쿠버네티스 전체 상태(etcd)는 **백업 자체가 없음** | 업그레이드 실패 시 되돌릴 방법이 없음 |

공통 원인은 하나였습니다. **"보이지 않았다."** gimpo 는 이 문제를 보이게 만들고, 복구까지 자동으로 확인합니다.

## 2. 제품 한 줄 정의

> 쿠버네티스의 **앱 데이터·설정·클러스터 상태**를 세 겹으로 백업하고, 매일 **실제로 복구해 보며**, 이상이 생기면 **신호등처럼** 알려 주는 웹 대시보드.

## 3. 핵심 가치

| 가치 | 무엇이 달라지나 |
|---|---|
| 🟢 **보인다** | 백업·저장소·작업·복구 상태를 1분마다 점검해 🟢🟡🔴 로 표시. 멈춘 작업도 4시간 안에 빨간불 |
| 🔁 **증명한다** | 매일 새 날짜가 찍힌 테스트 데이터로 "백업 → 삭제 → 복구 → 비교", etcd 는 임시 클러스터에 복원해 검증 |
| 🧭 **쉽다** | 한국 시간 일정 편집, 알아보기 쉬운 표시 이름, 복구 화면에서 네임스페이스 바꿔 미리 확인 |
| 🛡️ **안전하다** | 로그인·페이지별 권한, 쓰기는 관리자만, 비밀 값은 화면·로그에 남기지 않음, 위험한 롤백은 절차서로만 |
| 📦 **분리한다** | 설정은 MinIO, 데이터는 물리적으로 다른 SeaweedFS — 한 저장소가 망가져도 다른 쪽이 남음 |

## 4. 기능 상세

### 4.1 세 겹 백업 설계
| 층 | 지키는 것 | 주기 | 보관 | 저장소 |
|---|---|---|---|---|
| 설정 백업 | 모든 리소스 정의(YAML) | 매일 | 30일 | MinIO |
| 데이터 백업 | 앱의 PVC 데이터 + 정의 | 매일(주요 앱) / 매월(전체) | 7일 / 35일 | SeaweedFS |
| etcd 스냅샷 | 쿠버네티스 전체 상태 | 6시간마다 | 7일(최소 3개) | SeaweedFS |

- 데이터 백업은 **앱 단위로 완결**되어 복구가 한 번에 끝납니다(설정과 데이터를 따로 맞출 필요 없음).
- 새 네임스페이스가 생겨도 월간 백업은 "전체" 기준이라 **빠지지 않습니다**.

### 4.2 상태 점검
- 서버·노드 에이전트·저장소·스케줄별 백업·멈춘 작업·삭제 대기·저장소 정리·복구 테스트·etcd 를 **한 화면**에.
- "예정 시각에 백업이 안 돌았다"를 일정(cron)에서 계산해 잡아냅니다. 백업이 만료돼 목록에 없어도 오탐하지 않습니다.
- 개요 화면 맨 위 배너 하나로 전체 상태를 판단합니다.

### 4.3 자동 복구 테스트 (Velero)
- 매일 05:00, 전용 네임스페이스에 **그날 날짜가 들어간** Pod·디스크(PVC)·설정·비밀을 만들고 → 백업 → 지우고 → 복구 → 4가지를 비교.
- 디스크 안 1MiB 난수의 지문(sha256)까지 비교하고, 복구된 디스크가 "새로 쓴 것"이 아니라 "복원된 것"인지도 확인합니다.
- 단계별 진행 상황과 이력이 화면에 남고, 실패하면 원인 분석을 위해 리소스를 남겨 둡니다.

### 4.4 etcd 백업 · 복원 연습 · 롤백 절차서
- 컨트롤 플레인 노드에 설치된 etcd 도구를 그대로 써서 **버전 불일치가 없습니다**.
- 매일 최신 스냅샷을 **임시 etcd 에 복원**해 리비전·핵심 데이터를 확인(운영 etcd 는 건드리지 않음).
- 스냅샷마다 **이 클러스터 값이 채워진 롤백 절차서**를 만들어 줍니다 — 노드별 명령, 확인 명령, 되돌리기까지.
- 절차서 명령은 3노드 클러스터에서 실제로 실행해 **스냅샷 시점으로 정확히 돌아가는 것**을 검증했습니다.

### 4.5 스케줄 관리
- 매일/매주/매월 + 시각을 **한국 시간**으로 고르면 다음 실행 3회를 미리 보여 줍니다.
- 표시 이름·설명은 언제든 변경. 실제 이름 변경 시 기존 백업을 **이력에 연결 / 유지 / 삭제** 중 선택.
- 스케줄별 이력에서 이름이 바뀌기 전 백업까지 함께 봅니다.

### 4.6 백업·복구 작업
- 백업 상세(포함 리소스·볼륨·경고/오류)·실행 로그를 웹에서 바로.
- 복구 시 **네임스페이스 매핑**으로 원본 옆에 복구해 먼저 확인하고, 문제가 없을 때 실제 복구.

### 4.7 자동 정리
- 끝난 저장소 정리 잡을 1시간마다 정리(저장소당 최신 1개만 남김) — 클러스터에 완료 파드가 쌓이지 않습니다.

### 4.8 계정과 권한
- 관리자 / 일반 사용자. 일반 사용자는 허용된 페이지를 **조회만** 합니다.
- 공통 플랫폼 로그인(PBKDF2 암호 저장, HttpOnly 세션 쿠키).

## 5. 사용 시나리오

| 상황 | gimpo 에서 |
|---|---|
| 아침 출근 | 개요 배너 🟢 확인 — 끝 |
| "어제 지운 데이터 살려 주세요" | 복구 → 최신 데이터 백업 → 원본 옆에 복구해 확인 → 실제 복구 |
| 쿠버네티스 업그레이드 전 | etcd → 지금 스냅샷 → 이 스냅샷으로 연습 성공 확인 → 절차서 저장 |
| 백업 시각을 업무 시간 밖으로 | 스케줄 → 편집 → 한국 시간으로 선택 |
| 감사·점검 대응 | 상태 점검·복구 테스트 이력으로 "매일 복구 검증" 증빙 |

## 6. 도입 효과 (이 클러스터 기준)

| 지표 | 도입 전 | 도입 후 |
|---|---|---|
| 정상 완료 백업 | 0건(검증 실패·멈춤) | 매일 성공, 오류 0 |
| 문제 인지 시간 | 몇 주(인지 못 함) | 최대 1분 점검 주기, 멈춤은 4시간 내 🔴 |
| 복구 가능성 확인 | 없음 | 매일 자동(Velero 05:00, etcd 05:30) |
| etcd 백업 | 없음 | 6시간마다, 매일 복원 검증 |
| 백업 저장소 사용률 | NAS 86% | 11% |
| 앱 데이터 일일 백업 시간 | 26~48분 | 24초(중복 제거) |
| 쌓인 완료 파드 | 123개 | 저장소당 1개 |

## 7. 구성 요구 사항

- 쿠버네티스 1.27+ (검증: 1.34), Velero 1.18 + node-agent, kopia 파일 백업
- S3 호환 저장소 1~2곳(권장: 설정과 데이터 분리)
- etcd 백업: Kubespray systemd 방식 etcd(바이너리 `/usr/local/bin`, `/etc/etcd.env`, `/etc/ssl/etcd/ssl`)
- ArgoCD(선택, GitOps 배포), 내부 컨테이너 레지스트리
