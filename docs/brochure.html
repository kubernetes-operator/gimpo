백업이 있는지가 아니라,

Why

문제는 백업 도구가 아니라 보이지 않는 것이었습니다

도입 전 이 클러스터에서는 설정 오류로 몇 주간 모든 백업이 실패했습니다. 볼륨 백업 하나는 13일째 멈춰 뒤로 17건이 밀렸고, 처리되지 않은 삭제 요청이 79건 쌓여 있었습니다. 아무도 몰랐습니다.

Design

세 겹 백업, 서로 다른 저장소

설정과 데이터를 물리적으로 다른 저장소에 둡니다. 한쪽이 망가져도 다른 쪽이 남습니다. 앱 데이터 백업은 그 자체로 완결돼 복구가 한 번에 끝납니다.

Proof

복구가 되는지 이렇게 확인합니다

Velero 자동 복구 테스트

매일 05:00
  1. 그날 날짜가 찍힌 Pod, 디스크, 설정, 비밀 생성
  2. 데이터 저장소로 백업
  3. 전부 삭제해 장애 재현
  4. 백업에서 복구
  5. 설정, 비밀, 파일, 1MiB 데이터 지문(sha256) 비교
  6. 복구된 디스크가 새로 쓴 것이 아닌지 확인한 뒤 정리

Features

운영하는 사람을 위한 기능

한눈에 보는 상태 점검

서버, 저장소, 스케줄, 멈춘 작업, 복구 검증, etcd 를 1분마다 점검합니다. 예정 시각에 백업이 안 돌면 바로 경고합니다.

한국 시간 스케줄

매일, 매주, 매월과 시각을 고르면 다음 실행 3회를 미리 보여 줍니다.

표시 이름과 이력

알아보기 쉬운 이름을 붙이고, 이름을 바꿔도 과거 백업을 이어서 봅니다.

옆에 복구해 보기

네임스페이스를 바꿔 원본 옆에 복구하고, 확인한 뒤 실제 복구합니다.

etcd 롤백 절차서

노드별 명령, 확인 명령, 되돌리기까지 담습니다. 위험한 작업은 웹에서 실행하지 않습니다.

로그인과 페이지 권한

관리자만 실행하고 변경합니다. 일반 사용자는 허용된 화면만 조회합니다. 비밀 값은 어디에도 남기지 않습니다.
